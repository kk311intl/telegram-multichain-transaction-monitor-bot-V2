# 執行、恢復與限速

- 全鏈下載、地址匹配、交易核對、通知和資料庫各自分離。Worker 只回傳命中交易身分，不持有 Telegram Token 或用戶 ID；協調器重新查詢交易核對，不直接信任命中內容。
- 租約 20 秒、心跳預設 5 秒；節點逾 45 秒失聯或鏈持續不健康 120 秒可轉到 `primary_node`。不把主節點的工作轉到其他節點，恢復節點也不自動搶回；主動 rebalance 先 drain，等待租約和緩衝結束才接手。
- 每次掃描啟動／重啟／接管從當時最新鏈頭開始，不追停機歷史。相同運行期間可重試批次、核對重組及回退最近 128 塊；超出可確認範圍停止推進並恢復，不偽造成功。
- 批次核對區塊號、hash、父鏈、交易／日誌一致性及重複索引，完整成功才提交游標。HyperEVM 額外核對收據，同批保持同一端點，不拼接不一致的供應商資料。
- 120 秒掃描循環完全無回應才判為卡死：先保存 `watchdog.json`（階段、進度、RPC 索引／方法／耗時，不含端點 URL 或密鑰），再退出並由 Worker 重啟。持續收到錯誤／等待 RPC 冷卻時標示重試，不因無新區塊反覆重啟或跳游標；持續不健康 120 秒仍可轉由主節點接管。10 分鐘內第三次程序異常冷卻 180 秒。租約失效、父程序未續期時自行退出，舊 epoch 回報仍被拒絕。
- 所有鏈共用有界 RPC：單次邏輯查詢共 30 秒，每端點最多 15 秒，為換源留時間；整批最多 50 秒、每端點 25 秒且最多兩個來源，區塊執行緒和收據查詢共用整批期限；整段重組查找最多 15 秒。慢批次縮小後重試，不放寬鏈身分、收據或完整性校驗。系統 DNS 若阻塞仍由 120 秒看門狗兜底。
- BTC 下載完整區塊及 prevout，逐地址計算輸入／輸出差額；SOL 以實際產塊 slot 前進，不把跳過的 slot 當作遺漏。兩者均核對父區塊與批次末端 hash，協調器再次從 canonical block 核對交易身分。SOL 以後繼區塊的 parentSlot 證明某 slot 在新分叉上不存在，才標為重組；RPC 缺資料或超時只延後核對。確認採 BTC 鏈頭減確認距離、SOL finalized；支援與其他鏈相同的通知更新、用戶隔離、持久快取及地址匯入匯出。
- RPC 優選按完整批次吞吐、錯誤與限流程度排序；已校驗批次的新速度占平滑評分 75%，單次請求延遲占 60%，好的端點可快速前移。每 30 秒至多試一個合格備用端點，失敗仍回到可用端點。背景資格檢查另行執行，合格端點少於 3 個時每 10 秒補測一個，其餘每 30 秒；優先尚未合格且冷卻已結束的候選，跳過冷卻端點，已有延遲樣本不被多次請求的資格檢查耗時覆蓋。健康狀態／資格快取綁定鏈身分；失敗換源仍須通過身分及資料校驗。
- HyperEVM 候選含 HyperLend Archive 與 Hyperliquid 官方 RPC。官方端點以 `genesis_optional_rpc_urls` 明確免查創世區塊；仍驗證鏈 ID、完整區塊與日誌，最新區塊不得舊於 180 秒、超前本機時間 120 秒或落後已見最高高度超過 128 塊。其餘端點維持創世 hash 校驗。
- RPC HTTPS 優先連 IPv4，失敗仍可回退 IPv6；每個位址 TCP 連線最多 3 秒，同次解析結果共用連線期限，避免壞的 IPv6 路由反覆耗盡資格檢測時間。TLS 憑證、主機名及鏈資料校驗維持啟用；系統 DNS 解析本身仍受作業系統期限控制。可用數指已通過資格檢查的端點，不代表所有候選都支援免費全鏈下載。
- RPC HTTP 429、JSON-RPC／TRON 明確限流共用階梯：60／120／300／600／900 秒；同一波在途失敗不重複升級。`Retry-After` 支援秒數及 HTTP 日期，較長期限優先，最多保留 24 小時。恢復後每端點發送間隔為 0.25／0.5／1／2／4 秒，批次執行緒、資格檢查共用同一客戶端的閘門；其他端點仍可服務。冷卻結束後 10 分鐘未再限流且有成功請求才降一級，其後每 2 分鐘成功降一級；單次成功不清空限流記憶。掃描器的階級、冷卻及恢復期限保存於健康快取，重啟不歸零；不同程序／不同 URL 不共用供應商帳戶配額。
- RPC 不跟隨重新導向，避免自訂認證標頭被轉送。資格檢測與交易請求都核對回應 ID；多源核對也拒絕錯配回應。錯誤只保留代碼，不把供應商可能回顯的憑證寫進日誌。限流策略集中於 `monitor/rpc_policy.py`，不改 Telegram 的通知節流。
- 命中資料快取預設 256 MiB，`RECENT_CACHE_MIB` 可設 1–65536；這是容量上限，不預先分配。進程的 systemd 記憶體上限另由部署者設定，須為其他資料留空間。
- 用戶授權與地址所有權在解碼後、發送前重查；每用戶獨立 delivery。資料庫唯一事件 ID 防重，Telegram 與資料庫之間無跨系統原子交易，不承諾 exactly-once。
- GoPlus 風險信號與 DEX Screener 市場過濾混合使用。已知風險直接阻擋；GoPlus 非風險／不可用再檢查市場。流動性 US$10,000、轉帳 US$1 是預設門檻；結果／價格快取 24 小時。可在鏈設定調整已有門檻；沒有穩定幣白名單。兩項都無法判定才顯示未知警告，不把未知當真幣保證。

## Telegram 限速與冷卻

- 每帳戶通知預設至少 5 秒，新通知、確認編輯及高頻移除提示共用。主動菜單無帳戶分鐘／秒配額且優先；背景清理／狀態更新每帳戶預設至少 1 秒。所有 API 預設共用至少 50ms 的實際送出間隔。
- 第一次 429 依 `retry_after` 暫停該帳戶；無有效期限則 60 秒。輪詢另計冷卻，無帳戶管理 API 使用全域冷卻。期限持久化，重啟不清零；運行期間使用單調時鐘，校時後同步保存期限。
- 冷卻中的用戶指令略過、不重播，需到期後重新操作；掃描與其他用戶繼續。因冷卻產生的舊積壓不作高頻刪址依據，恢復後另有 120 秒保護期。
- 排程先檢查可發時間，空隊列每秒檢查，單用戶最多一個發送工作、最多 32 用戶並行。排隊期間已確認只發最新狀態；若送出途中狀態改變，後續仍可能需要編輯。
- 非通知消息預設 10 分鐘清理，不置頂。運行狀態只顯示自己的地址／待通知總數及各鏈狀態，不顯示帳戶通知診斷。近 10 分鐘 429 最多保存 128 筆，只觀測，不自行推定全 Bot 限流。
